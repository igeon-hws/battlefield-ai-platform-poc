# ADR — Architecture Decision Records

## 선언적 온톨로지·업무 질의·Fabric 정의 발행 — 2026-10-29

발표 메시지(같은 지식이라도 지식베이스로 구조화하면 더 일관되고, 추적 가능하고, 바꾸기 쉬운 답)를 검증 가능하게 만들기 위해 지식 정의를 코드에서 선언 하나로 옮긴다. 선언은 Fabric 문서 ONTOLOGY-01로 지식 집합에 들어가 B의 렌더링 본문과 C의 Graph 규칙·업무 질의를 같은 version/hash로 고정한다. 문서와 Graph를 따로 맞추던 검토 부담과 불일치 위험이 줄고 B↔C가 같은 지식이라는 주장이 구조적으로 성립한다. 대가로 업무 질의의 연산자 종류는 여전히 코드이며 새 유형의 질의는 코드와 선언을 함께 바꿔야 한다. OWL/RDF 같은 형식 언어나 범용 추론기는 도입하지 않는다.

C의 원시 Semantic 도구를 LLM이 조립하던 구조가 비용·예산 실패의 원인이었으므로 업무 질의 단위를 추가한다. 업무 질의는 Graph의 검증된 연결과 같은 build에 고정된 원천 snapshot을 함께 읽어 Graph/원천 책임 경계를 유지한다. 원시 도구는 미포함 질문을 위해 유지한다. C′(원시 도구만) 조건을 두지 않기로 해(사용자 결정) Graph·규칙 실행과 업무 질의 추상화의 효과를 분리하지 못한다. 업무 질의를 평가 질문에 맞춰 만든다는 비판을 줄이기 위해 질문 그룹(포함/조합/미포함/대조군)과 hold-out을 두고 그룹별로만 보고한다.

정의 변경은 Fabric이 소유하므로 Fabric UI에 편집·검증·영향 분석·승인·발행 쓰기 경로를 추가한다. "Fabric Graph 탐색" 결정의 읽기 전용 원칙을 정의 발행에 한해 부분 변경한다. 편집은 선언의 `editable` 항목만, 승인은 작성자와 다른 사람만 가능하고 발행은 새 불변 버전을 만든다. 기존 버전·Graph·완료 run은 바뀌지 않고 진행 중인 대화는 시작 버전을 유지한다. 대가로 로컬 파일 store의 동시 발행 직렬화, 운영 수준 인증·권한, 발행 취소는 제공하지 않는다(되돌리기는 이전 값으로 새 버전을 발행). Agent에는 편집 도구를 주지 않는다.

계획의 새 원천 dataset 대신 v5 원천을 그대로 쓰고 지식 계층만 v6로 분리한다. 발표 직전 세 Mock 체계 변경 위험을 피하고 v5 원천에 이미 있는 함정(공동지원·상태 미상·정정 보고·작업별 예약)을 쓴다. 대가로 규칙 상호작용·시간 의미를 새로 늘린 데이터는 없으며 규모 효과는 다루지 않는다. 선택은 `C4I_ONTOLOGY_PROFILE=6`(dev.py 기본)이고 v5 지식 계층과 그 평가 이력은 profile 5로 보존한다.

## 의미 조회 범위와 run 내 근거 재사용 — 2026-10-28

사용자 REVIEW의 C 도구 비효율을 Semantic MCP/단일 Agent 구조를 유지한 채 줄인다. `interpret_concept`는 키워드 유사 검색이나 전체 규칙 반환 대신 검토된 용어→시작 ruleId 표와 명시적 의존만 사용한다. 재현 가능하고 근거가 분명한 대신 표에 없는 용어는 `unresolved`가 되며 새 용어는 검토 후 추가해야 한다. 구형 전체 조회는 명시적 `all`로만 유지한다. 절차 도구는 SOP-01 기본값을 없애고 documentId를 요구하며 정비/복구 미지원을 설명한다.

원천 응답 재사용은 run 범위와 전체 snapshot 핀으로 한정해 다른 시점·run의 근거 혼입을 막는다. 실제 원천 요청은 줄지만 모델의 도구 호출 수와 예산 소모는 그대로이므로 근본적인 반복 선택은 별도 관측 대상이다. 예산 소진 시 마지막 한 번은 도구 없이 답변을 요청한다. 한도를 늘리지 않고 partial 답변 기회를 주는 대가로, 확인하지 못한 항목의 명시는 모델에 의존한다.

A 공통 프롬프트의 `laborHours` 정의를 제거하고 질문에 없는 L3 18:00 판정을 gold에서 뺐다. 이는 프롬프트 digest와 v5 gold를 바꾸므로 2026-10-28 9-run 사전 평가와 이후 측정은 같은 기준의 반복이 아니다. 기존 artifact는 수정하지 않는다.

## 업무 표현과 의미 판정의 분리 — 2026-10-28

객체 선택에 새 모델 요약을 붙이는 대신 Fabric의 검증된 연결과 live 원천 기록에서 결정론적 업무 view를 구성한다. DISPLAY-01을 B/C 공통 지식 집합에 추가하고 C API/MCP와 업무 view가 같은 version/hash의 표현을 사용한다. 원천 단독 UI에는 로컬 표시 자산을 둬 Fabric 의존을 만들지 않는다. 원천 상태 번역은 공통 가용 판정이나 동일성 규칙 실행이 아니며 aliases도 동일성 근거가 아니다. 기존 laborHours를 경과 시간(h)으로 유지해 기존 전망 계산을 바꾸지 않는다.

의미 상황판은 명시적 동일성만 재사용하고 위치가 다른 관측을 삭제하지 않는다. 대표 위치 정책이 없으므로 자산별 관측 목록과 근거를 제공하는 대가로 한 자산의 마커가 여러 개 남는다. 평가에는 같은 pins/지식/모델 설정을 재사용하고 실제 usage·실패를 보존한다. 토큰 중단 기준은 ABC 사이에서 검사하는 관측 한도이며 이미 진행 중인 비교의 비용 상한을 보장하지 않는다. 실제 모델 효과는 무과금 기능 검사와 구분하고 사용자 요청에 따라 이번에는 측정하지 않는다.

현재 기술 계약은 [ARCHITECTURE](ARCHITECTURE.md), 실제 검증은 [IMPLEMENTATION_STATUS](IMPLEMENTATION_STATUS.md)가 기준이다. 이 문서는 결정 이유·영향만 남긴다. 아래 기존 번호를 보존하며 중복됐던 ADR-023은 v3 결정과 S8 역사 항목으로 구분한다.

## ADR-023 — Native C2 + Data Fabric v3 (2026-10-22)

원천별 native SQL/API/UI를 분리하고 공유 runtime을 기계 기능으로 한정한다. 기존 semantic-api를 Fabric API/콘솔로 확장해 gateway/브로커를 추가하지 않는다. 검토 문서 hash/version·명시적 adapter·JSON 규칙·Neo4j 저장을 분리한다. 범용 추론 엔진 도입은 유보한다.

OFF는 native 문서/일반 계산이며 ON만 Semantic 해석·조건 평가를 추가한다. 원천 지식을 숨겨 인위적인 차이를 만들지 않는다. 집계는 current-run 페이지·범위·동일성·상태·정책 근거를 요구한다. 일부 빈 조회를0으로 확정하지 않으며 유형×상태 계산을 제공한다. 모델의 수동 표 작성 사례 때문에 실행 완료와 검증된 정답을 분리한다. v2 호환 분기·명시적 규칙 검토가 유지 비용이다.

## S8 결정 — 과거 중복 ADR-023 (2026-10-16)

초기 ADR-021의 공유 로컬 계산에서 Semantic helper가 실행될 여지를 대체했다. OFF는 간접 의미 해석/ER까지 차단하고 ON은 실제 Semantic 근거를 계산에 적용한다. 지도/Builder 변환을 OFF 근거로 주입하지 않는다. 정책이 다른 대화를 이어 쓰지 않는다. 기본 v2 데이터에서 의도적 동일 자산 상태 충돌을 제거했다. 이전 격리 정책의 비교 결과를 새 정책 평가에 재사용하지 않는다.

## Fabric Graph 탐색 — 2026-10-26

읽기 전용 Fabric UI가 버전을 고정한 제한된 부분 그래프를 Semantic API로 조회한다. 임의 Cypher/Neo4j 브라우저 직접 접속이나 Agent 도구 확장 없이 기존 인증·근거 경계를 유지한다. UI는 추가 그래프 라이브러리 대신 SVG와 결정론적 배치를 사용한다. 이는 제한된 PoC 크기에 적합하지만 대규모 배치·분석 기능은 제공하지 않는다.

기존 불변 READY Graph의 domainJson을 DB에서 조건·상한과 함께 읽는다. 기존 Graph를 수정하거나 다시 생성하지 않고 탐색할 수 있는 대신 JSON 검색/정렬의 DB 스캔 비용은 남는다. 버전 목록은 생성 시각/ID keyset으로 페이지를 나눠 새 build 추가 시 중복을 방지한다. 사람이 읽는 생성 시각·데이터셋·짧은 ID는 표시용이며 모든 실제 조회는 전체 graphVersion을 사용한다.

## Fabric 지식 소유권과 A/B/C 비교 — 2026-10-26

레거시 체계 API에 LLM용 설명 문서가 이미 있다는 가정을 제거한다. 업무 보고·명시적 관계는 원천에 남기고 설명 문서8개는 hash/version을 보존해 Fabric에 이관한다. 공통 정책 보완 문서를 추가해 C의 해석에 필요한 기본값/예외를 B에도 제공한다. 관리 주체와 발행·적용 체계는 구분한다.

A↔B로 추가 지식 접근, B↔C로 동일 지식의 구조화·규칙 재사용 체계를 비교한다. C에는 평가 helper도 있으므로 Graph 저장만의 효과라고 주장하지 않는다. B는 실제 Knowledge MCP를 사용하며 Graph 없이 동작한다. 지식 version/hash는 불변 archive로 보존하고 원천 snapshot과 독립적으로 고정한다. 일반적인 문서 수집/임베딩/LLM 추출 대신 검토된 패키지 catalog와 literal 검색을 사용하므로 작고 재현 가능하지만 새 지식 등록은 검토·배포가 필요하다.

원천 문서 제거는 파괴적 계약 변경이므로 v4/schema·ontology·adapter4/정책4-knowledge-abc와 별도 DB를 도입한다. v3의 문서 허용 OFF/ON·Graph·평가 결과는 원래 의미로 보존한다. 하나의 Agent loop를 재사용하고 별도 Orchestrator는 도입하지 않는다.

## 지도·AI 채팅 통합 — 2026-10-27

사용자 REVIEW에 따라 v4의 세로 분석 폼과 접힌 지도를 viewport 안의 지도·채팅 작업 화면으로 교체한다. 같은 SituationMap과 공통 RunPanel을 재사용해 지도 상태와 근거/방책 동작을 유지하고, 비교는 채팅 탭과 명시적 확대 화면으로 제공한다. 대화 본문과 지도 UI 상태만 연결하며 지도 선택을 새 Agent 근거로 주입하지 않는다. 별도 backend/Agent 정책은 추가하지 않는 대신 UI가 capped 목록 밖의 선택 비교/실행을 추가 조회하고, 짧은 화면에서는 지도 높이를 줄이는 대가를 수용한다. v4 CSS를 `.bf-shell`에 한정해 원천/Fabric/v3 화면과 격리한다.

## 세 체계와 Agent 독립 조회·페이지 격리 — 2026-10-28

군수 체계를 독립 원천으로 추가해 자산 동일성·정비·부품/예약·수송이라는 연결의 재사용을 검토한다. 기존 기대값을 바꾸는 대신 v5 dataset/schema/policy·DB·fixture를 분리해 v4/v3 이력을 보존한다. 설명 문서는 Fabric 소유이며 B/C의 같은10개 지식 집합을 사용한다. 복구 전망의 정답을 C에만 주지 않고 같은 문서로 B도 해석할 수 있게 한다.

객체 클릭의 통합 상세는 Agent가 아닌 Fabric 서비스가 담당한다. Semantic은 검증된 연결·기간·근거를, 원천은 live 사실을 소유한다. UI와 MCP는 의미 해소 서비스를 재사용하지만 Agent가 live Fabric 상세로 원천 MCP를 우회하지 않는다. 최초 Graph 준비의 지연/장애와 현재 원천의 부분 단절을 구분하는 비용을 수용한다.

A/B/C는 공통 shell의 별도 진입과 서버 context로 제한한다. UI 편의성 차이는 보여 주되 공식 모델 비교는 별도 고정 snapshot 화면에 둔다. opaque context는 운영 인증이 아닌 데모 capability이며 사용자는 다른 조건에 명시적으로 진입할 수 있다. A/B의 세 원천·원천 매핑 접근은 유지하고 C 결과/캐시가 자동 유입되는 것을 막는다. 실제 모델 효과와 단순 구현/도구 실행 성공은 별도로 기록한다.

## 주장 종류와 인용 출처 분리 — 2026-10-28

B가 문서 해석을 semantic으로 표기하거나 본문의 규칙 이름을 ruleRefs로 옮기면 유효할 수 있는 답변 전체가 버려졌다. semantic은 사고 종류와 도구 출처가 섞인 값이므로 새 A/B/C 모델 스키마에서 제외하고 실제 출처는 서버의 run 근거로 산출한다. 구형 표기는 보수적 모델 해석으로 보존하며 실제 A/B의 Semantic 접근은 계속 금지한다.

규칙 이름이 문서에 존재하는 것과 구조화된 규칙 근거를 구분한다. 문서 표기는 문서 근거로, 확인 불가 표기는 경고/partial로 보존한다. 이로써 분류 오류의 반복 모델 호출을 줄이되 잘못된 근거 ID는 계속 실패시킨다. 자연어의 진위/충분성은 자동 판정하지 않는다. 서버의 provenance1 응답 계약을 모델 출력 계약에서 분리하며 기존 실패 run을 재작성하지 않는다.
