> 근거: [REVIEW](REVIEW.md) 2026-10-29 두 번째 항목과 하위 항목. 직전 Implement(분석 과정 보기: 단계별 설명·제외 항목·작은 그래프)는 완료되어 [IMPLEMENTATION_STATUS](IMPLEMENTATION_STATUS.md)에 있다.

### 문제 (실제 run `4cadb5fe…`, "21일까지 준비되는 1사단 장비")

- 주장 4개가 근거 2개(가용 현황 `ev-29a0…`, L-T02 정비 체인 `ev-38e2…`)를 나눠 인용해 같은 분석 과정·그래프가 4번 그려졌다.
- 주장 분류 4종(원천 관측·근거 계산·모델 추론·Semantic 해석)은 모델이 붙인 값이라 보는 사람이 구분하기 어렵고 서버 확인 출처와 어긋난다(모델 "원천 관측" / 서버 출처 Semantic).
- "근거 계산" 주장 "조건부 포함 4대"는 3(업무 질의)+1을 LLM이 더한 값이다. 이 run에서는 계산 도구를 호출하지 않았다. 출처가 Semantic이라는 사실만으로는 코드가 결정한 값인지 알 수 없다.

### 범위

1. **근거 영역(분석 과정 1회 표시)**: C 답변의 주장 목록 위에 "근거" 영역을 두고, 주장들이 인용한 업무 질의 근거를 처음 인용된 순서로 근거당 한 번만 펼친다(업무 질의 이름·근거 ID, `AnalysisView`, 접힌 세부 근거). 주장 카드에서는 분석 과정을 그리지 않고 인용 근거 칩(업무 질의 이름)을 보여 주며, 칩을 누르면 해당 근거로 이동·강조한다. 인용되지 않은 업무 질의 근거(예: L-C01 정비 체인)는 "인용되지 않은 근거"로 접어서 보인다.
2. **서버 판정 주장 2분류**: provenance 주석에 서버가 판정한 `claimClass`(`fact` 계산된 사실 / `judgment` 모델 판단)와 사유를 추가한다. 규칙(결정적, LLM 미사용):
   - `fact`: 모델 분류가 추론이 아니고, 인용 근거에 업무 질의 또는 계산 도구(`semantic`·`computed`) 근거가 있으며, 주장 문장의 수치·시각 토큰(예: "3대", "15:00")이 모두 인용 근거 값 안에 있을 때.
   - `judgment`: 그 외 전부. 사유를 남긴다(모델 분류가 추론 / 근거에 없는 값 "4" / 업무 질의·계산 근거 없음).
   - 모델의 원래 분류는 삭제하지 않고 provenance에 보존해 툴팁으로만 보인다. 서버 검증 기준(근거 ID·규칙 확인)은 바꾸지 않는다.
3. **표시**: 주장 카드는 두 배지만 쓴다. "계산된 사실(코드가 결정)"은 차분한 표시, "모델 판단(LLM이 해석)"은 강조 테두리와 "검토 필요" 표시. 판정 사유를 한 줄로 보인다. 답변 상단에 "계산된 사실 N · 모델 판단 M" 요약을 둔다.

- 적용 대상은 C(structured) 답변이다. A/B 답변의 주장 표시는 이번 범위에서 바꾸지 않는다(업무 질의 근거가 없어 근거 영역이 비고 분류 의미가 다르다).
- 결과 계약(`AnalysisResult` claim provenance)에 필드를 추가하므로 계약 export와 프론트 타입을 함께 갱신한다. 이전 run(필드 없음)은 기존 표시를 유지한다.

### 제외

모델 프롬프트·도구 설명 변경(분류는 서버가 사후 판정), 계산 도구 사용 강제, A/B 표시 변경, 그래프 라벨 원시값 문제(구 그래프 빌드·정비 체인의 FORCE-SCOPE-01 제목)와 원시 의미 도구 중복 호출 — 아래 보류 항목으로 둔다.

### 먼저 실패시킬 테스트

- provenance 단위: run `4cadb5fe…`와 같은 형태의 근거·주장으로 "가용 3대(L-T01·L-U01·L-V01)" → `fact`, "조건부 포함 4대" → `judgment`(근거에 없는 값 4), 모델 추론 주장 → `judgment`, 원천만 인용 → `judgment`(업무 질의·계산 근거 없음), "15:00" 시각 토큰 일치 → `fact`. 모델 원래 분류 보존, 기존 규칙 검증 결과 불변.
- 브라우저(결정적 provider, 주장 3개가 근거 2개를 나눠 인용): 분석 과정이 근거 수만큼만 보임, 주장 카드에 분석 과정 없음·근거 칩 클릭 시 해당 근거 강조, 배지 두 종류와 "검토 필요", 요약 개수, 390px 넘침 없음. 기존 v6 흐름(근거 추적·발행)은 유지.

## 보류 중인 항목 (별도 지시 필요)

- 그래프 라벨 원시값: 라벨 추가 전에 빌드된 그래프(`domain-ee0c…`)는 개념·관계 라벨이 없어 `Unit`·`SUBORDINATE_TO`로 보인다. 그래프 재빌드 또는 빌드 버전에 선언 렌더러 버전 반영이 필요하다. 정비 체인 단계의 규칙 제목은 질의 선언 규칙(LOG-LINK-01)만 조회해 FORCE-SCOPE-01이 ID로 보인다.
- C가 업무 질의 대신 원시 의미 도구(`resolve_unit_scope`)를 반복 호출하는 경우(같은 run에서 2회).
- v6 유료 모델 평가(1단계 소규모 확인, 2단계 그룹×조건×반복). 명령은 ARCHITECTURE·STATUS에 있다.
- 브라우저 흐름에서 첫 C 업무 질의가 간헐적으로 60초를 넘는 원인 확인(데모 서버 Semantic API의 높은 CPU 사용, 업무 질의마다 그래프 전체 재로딩이 후보이며 미확인).
- Gemma4 사내 모델 선택: 게이트웨이가 `tools`·`response_format`을 허용하면 Chat Completions 어댑터로 진행. 프롬프트 기반 툴 호출은 native tool loop 경계 변경이라 ADR 결정이 필요하다.
