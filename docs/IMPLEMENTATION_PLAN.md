# IMPLEMENTATION_PLAN

## 다음 Implement: 지식베이스 효용 시연 — 일관성·추적 가능성·변경 용이성

> 진행 상태(2026-10-29): 사용자 지시로 M1·M2a·M2b·M3을 한 번에 구현했고 무과금 검증을 마쳐 Human Review 대기다. 실제 결과·계획과 달라진 점·미검증은 [IMPLEMENTATION_STATUS](IMPLEMENTATION_STATUS.md)에 있다. 남은 항목: 유료 모델 평가(별도 승인), 브라우저 흐름의 간헐적 업무 질의 지연 원인 확인. 계획과 달리 새 원천 dataset 대신 v5 원천을 재사용했고(7절), 업무 질의 후보 중 보고 계보·절차 진행은 구현하지 않았다(3절, 원시 도구로 대응).

### 근거와 전달할 메시지

- 반영 대상은 2026-10-29 사용자 검토 대화에서 합의한 방향이다. [REVIEW](REVIEW.md) 원문은 아직 직전 Semantic 효율 검토 내용이며 이 Reflect에서 수정하지 않았다. 사용자가 REVIEW에 원문을 남기면 차이를 이 계획에 다시 반영한다.
- 발표 메시지: **"같은 지식이라도 지식베이스(온톨로지·지식그래프)로 구조화하면, 더 일관되고, 추적 가능하고, 바꾸기 쉬운 답을 얻는다."** 이 계획의 모든 구현은 세 주장 중 하나를 측정 또는 시연으로 뒷받침해야 한다.

| 주장 | 뒷받침 방식 | B(문서 지식)와의 대비 |
| --- | --- | --- |
| ① 일관된 답 | A/B/C 반복 평가로 **측정** | 같은 문서를 읽은 B는 규칙 상호작용·시간 의미에서 반복 간 해석이 흔들리거나 틀릴 수 있다 |
| ② 추적 가능한 답 | C 답변→업무 질의→규칙·정의 버전→그래프 간선→원천 기록 **시연** | B는 문서를 인용하지만 정의 적용 과정은 LLM 내부에 있다 |
| ③ 바꾸기 쉬운 답 | 운용자가 Data Fabric UI에서 정의를 바꾸고 영향 분석·승인·발행하면 B 문서·C 결과·UI에 전파되는 **시연과 측정** | B는 문서만 바뀌고 반영은 LLM의 재해석에 의존한다. A는 반영할 곳이 없다 |

- 주장하지 않는 것: "LLM은 지식베이스 없이 못 한다", 규모에 따른 효용·성능, 지식그래프 저장 형식만의 효과. A/B의 올바른 답은 유효하며 실패를 분모에 포함한다. C′(원시 의미 도구만) 조건은 두지 않으므로(사용자 결정) B↔C 차이는 "선언적 온톨로지·지식그래프·업무 질의 계층 전체"의 효과로만 보고한다.
- 검토에서 확인한 현재 문제: 지식 정의가 Python adapter와 하드코딩 용어 표(`semantic_core/domain.py`)에 흩어져 있어 ③이 성립하지 않는다. C의 Semantic 도구가 원시 수준이라 LLM이 조립하며 비용·실패가 커진다(사전 평가 L2 C budget_exceeded, 단순 범위 질의 8 tools/97k tokens). 주장별 규칙 검증이 인용 evidence에 한정돼 올바른 C 답에도 규칙 미확인 경고가 붙어 ②가 결함처럼 보인다. 현재 v5 데이터는 작고 명시적이라 A/B도 정답에 도달하기 쉽다.
- 유지: 단일 Agent·OpenAI native tool loop, 실제 MCP Client→Server→공개 API, Graph는 검증된 의미·관계·근거/원천은 live 상태 소유, LLM 관계 생성 금지, 독립 gold.

### 범위와 제외

- 범위: v6 선언적 온톨로지와 컴파일러, 업무 질의 API/MCP, 정책6 A/B/C, 근거 추적 화면, Data Fabric UI의 정의 변경·영향 분석·승인·발행과 전파 시연, v6 소규모 dataset·fixture, 평가 도구, 진입 화면 문구, 영향받는 spec/ADR.
- 제외: 대규모 dataset·규모 축 비교·Cypher 순회 전환(사용자 결정으로 소규모만), C′ 조건, 선언 전체의 자유 편집·운영 수준 인증/권한 체계·Agent의 정의 편집 도구, v5/v4/v3 코드 경로·fixture·Graph·평가 artifact 변경, OWL/RDF 도입, LLM 기반 온톨로지 추출, 다중 Agent·Orchestrator, 승인 없는 유료 모델 실행.

### 마일스톤

범위가 커서 네 마일스톤으로 나눈다. 사용자는 마일스톤 단위로 Implement를 지시할 수 있고, 각 마일스톤 종료 시 검증 결과를 STATUS에 남겨 Human Review로 넘긴다.

- **M2b Fabric 정의 변경**: 6절. Data Fabric UI의 편집·검증·영향 분석·승인·발행과 전파 비교.

### 0. 선행 정리 (M1)

- 기존 실패 `test_graph_sync.py::test_builder_queues_and_restart_recovery_are_scoped_to_source_endpoints`의 대체 `build`를 worker의 `ensure_build(body, knowledge)` 계약에 맞춰 녹색 기준선에서 시작한다.
- Implement 시작 시 STEP/AGENTS 단계 표시만 Implement로 갱신한다.
- 구현·검증 후 갱신할 문서(해당 마일스톤 범위만): PRD(발표 메시지·세 주장·시연 흐름·평가 설계·소규모 한정), ARCHITECTURE(온톨로지→문서/Graph/업무 질의 생성, 정책6, 추적 경로, Fabric 쓰기 경로), ADR(선언적 단일 원천·업무 질의 수준·C′ 미도입·Fabric 읽기 전용 결정의 부분 변경과 그 대가), UI_GUIDE(진입 문구·추적 화면·정의 편집/영향 분석/변경 비교 화면), STATUS(실제 결과·한계).

### 1. 선언적 온톨로지 단일 원천 (M1, 주장 ③의 전제)

- `packages/ontology`에 v6 선언 패키지(JSON 또는 YAML)를 둔다. 포함: 개념/객체 유형, 원천 필드 매핑, 관계 유형과 방향, 역할(ORG/ATT/SUP/CTRL 등), 용어→시작 규칙, 규칙 정의와 명시적 의존, 업무 질의 정의(입력·범위·적용 규칙·집계·출력 의미), 표시 메타데이터, 원천 출처 문서 참조. 선언 version/hash를 하나로 산출한다.
- 선언 schema 검증: 미정의 규칙·관계 참조, 의존 순환, 용어 중복, 업무 질의가 참조하는 규칙/관계 존재. 오류 시 Graph build를 거부한다.
- v6에서 `interpret_concept`의 용어/의존 표를 선언에서 읽는다. 원천 필드 읽기·명시적 association 확인 adapter는 Python에 남길 수 있으나, 의미 판정(가용/범위/동일성 기준)은 선언에만 둔다. v5 이하 경로는 그대로 둔다.

### 2. 컴파일러: 같은 선언에서 B 문서와 C 실행 생성 (M1, 주장 ①③의 공정성)

- 렌더러: 선언 → B용 Fabric 문서(규칙·용어·관계·업무 질의 정의를 자연어와 표로). 문서에 선언 version/hash와 규칙/업무 질의 ID를 표기한다. 같은 선언은 같은 문서 hash를 낸다.
- 기존 원천 출처 문서(REF/ORG/EX/SOP/LOG/POLICY/DISPLAY)는 v6 지식 집합에서 선언의 출처 근거로 연결한다. B/C는 같은 v6 지식 집합 manifest/hash를 고정한다. v5 archive는 보존한다.
- 컴파일: 선언 → Graph Builder 입력(규칙·관계·업무 질의 정의 노드)과 Semantic 실행 정의. Graph build에 선언 hash를 기록하고 C run은 지식 집합 hash·선언 hash·Graph 버전 일치를 검사한다.
- 패리티 검사: 렌더링 문서의 규칙/업무 질의 ID 집합 = Graph의 규칙/업무 질의 ID 집합.

### 3. 업무 질의 Semantic Layer (M1, 주장 ①②)

- 선언된 업무 질의를 Semantic API와 Semantic MCP 도구로 노출한다. 업무 질의는 손으로 짠 별도 로직이 아니라 선언의 정의를 지식그래프의 검증된 연결 위에서 실행하는 창구로 구현하고 설명한다. 최소 후보(질문 작성 전에 확정): 부대 범위×유형×상태 자산 현황, 자산 교차 체계 동일성·의존 체인(정비→부품→재고/예약→화물→수송), 부품 수급 구분(보유·예약·비예약·입고 의존), 조건부 복구 전망 입력 수집(가정 포함), 보고 계보·정정, 절차 진행.
- 응답에 추적 정보를 구조화해 싣는다: 결과, 업무 질의 ID·정의 version, 적용 규칙 ID, 거친 그래프 노드/간선 key와 graphVersion, 원천 snapshot 핀과 원천 근거 참조, completeness/partial·unknown·미확정 사유. live 수치는 원천 공개 API에서 읽고 Graph를 live 출처로 쓰지 않는다. MCP 경계를 우회하지 않는 경로를 ARCHITECTURE에 확정한다.
- 원시 의미 도구는 C에 유지해 업무 질의가 다루지 않는 질문에 대응한다. 도구 설명에 사용 구분을 둔다.
- provenance: 주장이 업무 질의 evidence를 인용하면 그 안의 규칙 ID로 규칙 근거가 검증되게 한다. 올바른 C 답에 규칙 미확인 경고가 붙던 경우를 테스트로 고정하고 업무 질의 경로에서 해소되는지 확인한다. 검증 기준 자체는 완화하지 않는다. 답이 완결됐는데 "부분 결과"로 표시되는 원인을 확인해 모델 보고·경고·실제 partial을 구분해 표시한다.
- 소규모이므로 현재 버전 전체 로드 방식을 유지한다. Neo4j 역할을 ARCHITECTURE에 "버전 고정 의미 저장소"로 명시하고 규모 확장 시 재검토를 한계로 남긴다.

### 4. 정책6 A/B/C와 진입 화면 (M2a)

- 새 비교 정책 `6-ontology-abc`와 contract6. A: 원천 MCP. B: A+v6 지식 집합(Knowledge MCP). C: B+업무 질의+원시 의미 도구. A/B는 업무 질의·원시 의미 도구·평가 helper를 MCP capability와 서버 검사로 차단한다. 모든 조건이 같은 질문·snapshot 핀·모델·예산을 사용하고 대화를 격리한다.
- 진입 화면 C 문구를 지식베이스가 드러나게 바꾼다. 예: "같은 문서를 온톨로지와 지식그래프로 구조화해, 검증된 연결·규칙·근거를 업무 질의로 활용합니다." A/B 문구는 같은 지식 범위임을 유지해 정렬한다. 최종 문구는 UI_GUIDE에 둔다.

### 5. 근거 추적 화면 (M2a, 주장 ②)

- C 답변의 주장마다 "업무 질의 → 정의 version·적용 규칙 → 그래프 간선 → 원천 기록" 경로를 펼쳐 볼 수 있게 한다. 그래프 단계는 기존 Fabric 그래프 탐색 화면으로 같은 graphVersion·대상 key를 고정해 이동한다. 원천 단계는 snapshot 핀이 붙은 원본 기록을 연다.
- B 답변은 같은 자리에서 인용 문서·문서 version/hash와 "정의 적용은 모델 해석"임을 표시하고, A는 원천 기록만 표시한다. 세 조건의 근거 형태 차이를 비교 화면에서 나란히 보여 준다.
- 추적 경로의 모든 링크는 run에 고정된 버전만 사용하고, 현재 최신 Graph로 바꿔 열지 않는다.

### 6. Data Fabric UI 정의 변경과 전파 (M2b, 주장 ③)

현재 Fabric UI는 읽기 전용 결정(ADR "Fabric Graph 탐색")을 따른다. 이 절은 정의 변경에 한정한 쓰기 경로를 추가하며, 그 결정의 부분 변경과 대가를 구현 후 ADR에 기록한다.

- 편집 범위: 선언에서 `editable`로 표시한 항목만 폼으로 바꾼다. 시연 기본 후보는 가용 집계 정책의 제한(PMC) 포함 여부와 상태→가용 매핑이다. 선언 전체의 자유 편집, 개념/관계 유형 추가·삭제는 제외한다.
- 흐름: 초안 작성 → schema 검증 → 영향 분석과 diff → 승인 → 새 선언 version 발행 → B 문서 재렌더링·새 지식 집합 hash·새 Graph build. 각 단계 상태를 Fabric API/UI에 표시하고 실패 시 발행하지 않는다. 기존 version·지식 집합·Graph는 수정하지 않는다.
- 영향 분석: 선언의 규칙 의존·업무 질의 참조·표시 메타데이터 참조를 따라 변경이 닿는 규칙, 업무 질의, 객체 상세/상황판 항목, v6 평가 질문을 발행 전에 나열한다. 결정론적으로 계산하며 LLM을 쓰지 않는다. 문서 기반 B에는 없는 지식베이스 고유 기능으로 시연한다.
- 승인과 기록: 데모용 capability 수준의 작성자/승인자 구분과 시각·diff·영향 분석 결과를 version 이력에 남긴다. 운영 인증이 아님을 화면과 문서에 표시한다. Agent에는 편집 도구를 제공하지 않는다.
- 적용 범위: 이미 끝난 run·비교는 당시 version을 유지한다. 새 run은 사용자가 선택한(기본은 최신 발행) version을 고정한다. 진행 중 run에는 영향을 주지 않는다.
- 비교 화면: 같은 질문·같은 snapshot 핀으로 기본/변경 version의 A/B/C 결과를 나란히 보여 준다. C 결과 차이를 정의 diff·영향 분석과 연결해 표시한다. B는 새 문서를 읽고 새 정의를 따르는지, A는 정의 변경과 무관함을 보여 준다.
- 측정: 변경부터 발행 완료까지 걸린 시간, 코드 수정 없이 가능했는지(필요했다면 한계로 기록), 영향 분석 목록과 실제 변경 결과의 일치, C 결과의 결정론적 재현, 정의 변경 후 B/C의 새 정의 준수율(M3 반복 평가에 포함).
- 시연용 변경 정의의 기대값은 독립 fixture에 두고, UI로 발행한 결과가 그 기대값과 일치하는지 검증한다.

### 7. v6 dataset·질문·gold (M3, 주장 ①)

- `c2-ontology-demo-v6`(가칭) 소규모. v5 수준 객체 수를 유지하고 규칙 상호작용과 시간 의미로 B의 정의 직접 적용이 어려운 상황을 만든다(배정 유효 기간, 개명/previousName, 배속·지원·통제 구분, 공동지원 중복, 정정 계보, 확정 불가). 원천 독립 실행·명시적 관계만 사용하고 동일 자산 상태를 의도적으로 상충시키지 않는다.
- 업무 질의 목록과 선언 hash를 먼저 고정한 뒤 질문을 작성한다. 그룹: 포함(업무 질의 1개), 조합(여러 업무 질의 또는 원천 결합), 미포함(업무 질의가 다루지 않음), 단순 대조군(원천만으로 충분), 정의 변경(6절 Fabric UI로 발행한 변경 version). 일부는 hold-out으로 구현 중 프롬프트·도구 설명 조정에 쓰지 않는다.
- gold·금지 결론은 production 코드·업무 질의 결과와 독립된 fixture에 작성한다.

### 8. 평가 도구 (M3, 주장 ①③)

- manifest에 정책6, 조건, 질문 그룹, 선언 version/hash(기본·변경), 지식/Graph hash, hold-out, 반복 수를 고정한다.
- 핵심 사실·금지 결론은 fixture 기반 자동 판정을 추가하고, 근거 충분성·서술 품질은 Human Review 양식으로 남긴다. 자동 판정 한계를 결과에 표시한다.
- 주 지표(메시지 순): ① 반복 간 일관성(같은 질문의 핵심 사실 일치율), 금지 결론 위반, 확정 불가 상황의 비확정, 정답/부분/실패. ② 주장별 추적 완결성(구조화 규칙·그래프·원천 근거까지 이어진 주장 비율). ③ 정의 변경 후 새 정의 준수율. 보조 지표: 도구/모델 호출·중복률·토큰·loop 시간, C 업무 질의 선택 정확도·미포함 질문 대체·오적용.
- 그룹×조건별로 집계하고 전체 평균 하나로 우위를 표시하지 않는다. C 우위가 나오지 않은 항목도 그대로 보고한다.

### 먼저 실패시킬 테스트

- M1: 선언 schema 검증(미정의 참조·순환·중복 거부), 결정론적 렌더링 hash, 문서↔Graph 규칙/업무 질의 ID 패리티, v6 `interpret_concept`의 선언 사용, 업무 질의별 독립 fixture 대조와 partial/unknown/미확정 보존, 응답의 정의 version·규칙·그래프 key·snapshot 핀, 업무 질의 evidence 인용 시 규칙 미확인 경고 미발생, 완결된 답의 "부분 결과" 오표시 재현.
- M2a: A/B의 업무 질의·원시 도구 차단과 C의 hash 불일치 거부, 추적 경로가 run 고정 graphVersion/snapshot만 여는지.
- M2b: `editable` 외 항목 편집 거부, schema 오류 시 발행 거부, 영향 분석 목록의 결정론성과 실제 변경 결과 일치, 승인 없는 발행 거부, 발행된 version이 코드 변경 없이 문서·지식 hash·Graph·C 결과·객체 상세에 전파, 기존 version·완료된 run 불변, Agent 도구 목록에 편집 도구 없음.
- M3: manifest의 그룹/hold-out/조건/정의 version 고정, 일관성·추적 완결성·새 정의 준수율 집계, 자동 판정의 핵심 사실·금지 결론.

### 검증 방법

- 무과금 비UI 회귀, 실제 세 원천·MCP·Neo4j 통합(v6 및 v5 회귀), UI 정적 회귀(진입·추적·정의 편집/영향 분석/발행·변경 비교 화면, 데스크톱/모바일 캡처 확인), Ruff/mypy/계약 export.
- 결정론적 provider로 정책6 A/B/C 비교와 기본/변경 정의 비교의 저장 경로 확인, 평가 CLI 무과금 manifest(planned runs, executed 0).
- Fabric UI 정의 변경의 발행 소요 시간, 업무 질의 응답 시간을 관측값으로 기록한다.
- 실제 유료 모델 평가는 완료 조건에 포함하지 않는다. 별도 승인 시 1단계(소규모 확인)와 2단계(그룹×조건×반복, 정의 변경 포함)로 나눠 실행한다.

### 완료 조건

- 각 마일스톤의 테스트가 실패 확인 후 통과하고 기존 v5/v4/v3 회귀가 유지된다.
- M1: B 문서와 C 실행이 같은 선언 hash에서 생성되고 패리티가 통과하며, 업무 질의가 v6 fixture와 일치하고 추적 정보를 싣는다.
- M2a: C 답변에서 원천 기록까지 버전 고정 추적이 화면에서 동작한다.
- M2b: Fabric UI에서 편집 가능 항목을 바꿔 검증·영향 분석·승인·발행까지 완료되고, 발행된 version이 코드 수정 없이 B 문서·Graph·C 결과·화면에 전파되는 비교 화면이 동작한다.
- M3: 무과금 manifest가 정책6 조건·그룹·정의 version을 고정해 생성되고 세 주장의 지표를 집계한다.
- STATUS 한계에 소규모만 검증, C′ 부재로 계층 효과 분리 불가, 유료 측정 전에는 ①의 효과 미측정임을 명시한다. 각 마일스톤 구현·검증 후 결정 이유는 ADR, 기술/요구/화면은 ARCHITECTURE/PRD/UI_GUIDE에 반영하고 Human Review로 넘긴다.
